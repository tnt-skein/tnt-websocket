# WebSocket

```lua
router.get('/ws', websocket.handler(function(ws) ws:send('привет') end))
local ws = websocket.connect('ws://127.0.0.1:8080/ws', { timeout = 5 })
ws:receive(5)                                   --> { kind = 'text', data = 'привет' }
```

`tnt-websocket` — WebSocket (RFC 6455) для Tarantool: сервер на маршруте
роутера [`tnt-router`](https://github.com/tnt-skein/tnt-router) и клиент
`ws://` и `wss://`. Рукопожатие у него — обычный запрос по договору роутера:
маршрут, параметры пути, слои входа и маршрута (журнал, опознаватель,
вход по куке), отказ по договору границы HTTP. Согласие — ответ 101 с полем
`takeover`, после которого роутер отдаёт соединение сессии. Сообщения
сжимаются по RFC 7692 (`permessage-deflate`), когда это включено.

Зависимости: [`tnt-must`](https://github.com/tnt-skein/tnt-must) (проверки
аргументов), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock) (сроки
клиента и ожидания ответа на закрытие),
[`tnt-context`](https://github.com/tnt-skein/tnt-context) (сессия в контексте
запроса), [`tnt-hash`](https://github.com/tnt-skein/tnt-hash) (SHA-1 ответа
на ключ), [`tnt-log`](https://github.com/tnt-skein/tnt-log) (журнал),
[`tnt-external`](https://github.com/tnt-skein/tnt-external) (подмена внешних
средств в проверках), [`tnt-tls`](https://github.com/tnt-skein/tnt-tls)
(клиент `wss://`) и [`tnt-compress`](https://github.com/tnt-skein/tnt-compress)
(сжатие сообщений). Сам роутер пакету не нужен и зависимостью не объявлен:
ответ 101 — таблица, а соединение отдаёт подключение роутера
(`tnt.router.takeover`, раздел «Смена протокола: `takeover`» его документа).

## Зачем пакет

Живым страницам — чату, уведомлениям, таблицам, которые меняются на глазах,
состоянию кластера у оператора — сервер шлёт новое сам, не дожидаясь, пока
страницу перезагрузят. Это WebSocket (RFC 6455), а у Tarantool 3.8 CE его нет:
ни в ядре, ни среди официальных роков, а `http.server` соединение из рук
не выпускает — после ответа он ждёт на нём следующий запрос HTTP.

Пакет ставит WebSocket на маршрут роутера, а не рядом с ним отдельным
сервером на своём порту. Рукопожатие тогда — запрос, как любой другой: слои
входа, журнал, опознаватель и вход по куке, которые приложение уже поставило
на маршруты, действуют и на него, а отказ рисует обработчик отказов роутера.
Отдельному серверу всё это пришлось бы давать заново, и вход в соединение
жил бы по другим правилам, чем вход на страницу.

Отказ — пара `nil, err` с родом: закрытое той стороной соединение, молчание
дольше срока, непринятое рукопожатие — так бывает, и что делать дальше,
решает вызывающий. Негодный аргумент и негодная настройка — ошибка
программиста и бросок на строке вызывающего.

## Как пользоваться

Сервер — обработчик маршрута. Сессия — функция `(ws, request)`: соединение
и запрос рукопожатия со всем, что в него положили роутер и слои.

```lua
local router = require('tnt.router')
local websocket = require('tnt.websocket')

router.get('/ws/:room', websocket.handler(function(ws, request)
    ws:send('вы в комнате ' .. request.params.room)

    while true do
        local message, err = ws:receive()

        if message == nil then
            return                              -- закрыто: err.code, err.reason
        end

        ws:send(message.data, message.kind)     -- эхо
    end
end, { protocols = { 'echo.v1' } }))

local httpd = require('http.server').new('127.0.0.1', 8080, { log_requests = false, idle_timeout = 60 })

router.attach(httpd)
httpd:start()
```

Клиент — `connect`:

```lua
local ws, err = websocket.connect('ws://127.0.0.1:8080/ws/kitchen', { protocols = { 'echo.v1' }, timeout = 5 })

if ws == nil then
    return nil, err                             -- err.kind: unreachable либо refused
end

ws.protocol                                     --> echo.v1
ws:receive(5)                                   --> { kind = 'text', data = 'вы в комнате kitchen' }
ws:send('привет')                               --> true
ws:receive(5)                                   --> { kind = 'text', data = 'привет' }
ws:close()                                      --> true
ws.closed.code                                  --> 1000
```

### Что умеет фасад

| Вызов | Что отдаёт |
|---|---|
| `endpoint(session, opts)` | конечная точка: обработчик маршрута `handler` и его сессии (ниже) |
| `handler(session, opts)` | обработчик маршрута: ответ 101 либо отказ парой |
| `connect(url, opts)` | соединение либо `nil, err` |
| `NORMAL`, `GOING_AWAY`, … `TRY_AGAIN_LATER` | коды закрытия (ниже) |
| `TEXT`, `BINARY` | виды сообщений |
| `CLOSED`, `TIMEOUT`, `INVALID`, `REFUSED`, `UNREACHABLE` | роды отказа |

### Соединение

| Вызов | Что делает |
|---|---|
| `ws:receive(timeout)` | ждёт сообщение `{ kind, data }`; `nil, err` — закрыто либо срок |
| `ws:send(data, kind)` | шлёт сообщение одним кадром; `kind` — `text` (по умолчанию) либо `binary` |
| `ws:close(code, reason)` | закрывает: свой кадр закрытия и ответ той стороны |
| `ws:is_open()` | открыто ли |
| `ws.protocol` | подпротокол, о котором договорились, либо `nil` |
| `ws.compressed` | договорились ли о сжатии `permessage-deflate` |
| `ws.request` | запрос рукопожатия — у сервера |
| `ws.closed` | чем кончилось — у закрытого: отказ с `code` и `reason` |

Сессия, вернувшаяся без закрытия, закрывает соединение кодом 1000; упавшая —
кодом 1011, а подробность уходит в журнал («сессия WebSocket упала»,
с путём и причиной), не той стороне. Соединение живёт, пока идёт сессия:
она идёт в файбере соединения `http.server`, и вернуться из неё раньше
конца разговора значит его кончить.

Отказ — пара `nil, err`, `err` — таблица с родом; строкой она — свой текст:

| Род | Когда | Соединение |
|---|---|---|
| `closed` | закрыто: той стороной (`code`, `reason` — её), нами, обрывом (1006) | закрыто |
| `timeout` | `receive` не дождался сообщения; `send` не дождался очереди записи | живо |
| `invalid` | `send` текста не в UTF-8 — такое шлют видом `binary` | живо, ничего не ушло |
| `refused` | сервер не принял рукопожатие (`status`) или ответил не по RFC 6455 | — |
| `unreachable` | соединение не открылось, TLS не поднялся | — |

```lua
ws:receive(0.05)
--> nil, сообщения нет за 0.05 с
ws:send('\255\254')
--> nil, текст сообщения не в UTF-8: такое шлют видом binary
ws:send('\255\254', websocket.BINARY)            --> true
```

Негодный аргумент — бросок на строке вызывающего: не строка в `send`, вид не
из двух, отрицательный срок, код закрытия, который в кадре не ходит,
причина длиннее 123 байт или не в UTF-8.

```lua
ws:close(1005)
--> код закрытия 1005 в кадре не ходит: годятся 1000–1003, 1007–1014 и 3000–4999
```

### Конечная точка: закрыть все сессии

`httpd:stop()` закрывает только приём новых соединений: сессии после
ответа 101 живут без сервера, пока их не закроет одна из сторон. Узел,
который уходит молча, оставляет клиентам обрыв 1006, и те не знают,
что пора подключиться заново. Сессии, которые надо уметь закрыть, держит
конечная точка — `endpoint(session, opts)` с теми же сессией
и настройками, что у `handler`:

```lua
local chat = websocket.endpoint(echo)

router.get('/ws', chat.handler)
-- …
chat:count()                                            --> 2
chat:close_all(websocket.GOING_AWAY, 'узел уходит')     --> 2
httpd:stop()
```

| Вызов | Что делает |
|---|---|
| `chat.handler` | обработчик маршрута — тот же, что отдаёт `handler` |
| `chat:count()` | сколько сессий идёт сейчас |
| `chat:close_all(code, reason)` | закрывает соединения всех сессий и отдаёт, сколько закрыто |

`close_all` закрывает соединения разом, каждое в своём файбере, и ждёт,
пока закроются: сотня молчащих клиентов держит его один `close_timeout`,
а не сотню. Код по умолчанию — 1001 («сторона уходит»), причина — пустая;
негодные код и причина — бросок на строке вызывающего, даже когда сессий
нет. Соединение, которое уже закрывается, не трогается и в число
закрытых не входит. Сессия узнаёт о закрытии на ближайшем `receive`
или `send` и возвращается сама, и `count()` падает, когда она вернулась.

Сессии помнит сама конечная точка, а не общий на процесс реестр:
закрывает их тот, кто объявил маршрут, и чужие маршруты это не задевает.
Приложение, которое принимает на маршрут конечную точку целиком, а не один
`chat.handler`, может закрывать её сессии само, когда отключает роутер:
скажем, кодом 1012 при перечитывании конфигурации и 1001 — когда узел
уходит.

## Рукопожатие

Проверяется по RFC 6455 (§4.2.1), и каждый отказ — по договору границы HTTP:
роутер рисует его своим обработчиком отказов, как отказ любого обработчика.

| Что пришло | Ответ |
|---|---|
| способ не GET | 405, `Allow: GET` |
| нет `Upgrade: websocket` или `Connection: Upgrade` | 426, `Upgrade: websocket` |
| `Sec-WebSocket-Version` не 13 | 426, `Sec-WebSocket-Version: 13` |
| `Sec-WebSocket-Key` не 16 байт в base64 | 400 |
| `Origin` чужой страницы | 403 |
| сессий этого маршрута уже `max_connections` | 503 |

```lua
http_client.get('http://127.0.0.1:8080/ws/kitchen').status        --> 426
```

`Connection` — список: Firefox шлёт `keep-alive, Upgrade`, и оба слова
находятся без оглядки на регистр.

Проверка входа — слоем маршрута или своим обработчиком вокруг `handler`:
отказ до рукопожатия — обычный отказ роутера.

```lua
local talk = websocket.handler(session)

router.get('/ws', function(request)
    if request.identity == nil then
        return nil, { status = 401, message = 'нужен вход' }
    end

    return talk(request)
end)
```

### Источник страницы

Браузер шлёт куки на рукопожатие с чужой страницы так же, как со своей:
без проверки `Origin` любая страница в интернете открыла бы соединение
от имени вошедшего оператора (Cross-Site WebSocket Hijacking). Поэтому по
умолчанию пускается только своё: `https://` либо `http://` с тем же узлом,
что в `Host`.
Свой список — `origins`, `'*'` в нём пускает всех. Без `Origin` ходят
не браузеры — им запрет чужих страниц ни к чему, их пускают всегда.

```lua
websocket.handler(session, { origins = { 'https://panel.example.org' } })
```

За обратным прокси, который переписывает `Host` (у nginx по умолчанию —
`proxy_set_header Host $proxy_host`), свой источник перестаёт совпадать
с `Host`: прокси передаёт `Host $host`, либо источники называются списком.

### Подпротокол

Сервер берёт первый из своего списка `protocols`, который предложил клиент.
Не предложил ни одного — рукопожатие идёт без подпротокола (§4.2.2): решать,
годится ли это, — клиенту и сессии (`ws.protocol == nil`), а не серверу.

### Предел сессий

`max_connections` — сколько сессий маршрута идёт разом. Сверяется дважды:
на рукопожатии — отказом 503, пока ответ ещё не ушёл, и на самом соединении —
между ответом и сессией файбер уступает, и два рукопожатия успели бы пройти
одну сверку; лишнее тогда закрывается кодом 1013 («попробуйте позже»).

## Кадры и сообщения

Разбор строгий, каждое нарушение — разрыв с кодом, а не догадка:

| Что пришло | Код |
|---|---|
| зарезервированные биты без расширения, незнакомый код кадра | 1002 |
| бит сжатия RSV1 у продолжения или у управляющего кадра | 1002 |
| кадр клиента без маски, кадр сервера с маской | 1002 |
| управляющий кадр частями или длиннее 125 байт | 1002 |
| длина в восемь байт с поднятым старшим битом | 1002 |
| продолжение без начала, новое сообщение посреди прежнего | 1002 |
| кадр закрытия в один байт, код закрытия, который в кадре не ходит | 1002 |
| текст или причина закрытия не в UTF-8 | 1007 |
| сжатое сообщение не разжимается | 1007 |
| сообщение больше `max_message` — по кадрам либо разжатое | 1009 |
| конец потока без кадра закрытия, молчание и на ping | 1006 (в кадре не ходит) |

Нарушителю уходит кадр закрытия с кодом и без причины: подробность —
в свой журнал (предупреждение «та сторона нарушила протокол WebSocket»
с кодом и причиной), а не той стороне. Кадр данных длиннее оставшегося места
не читается вовсе: заявленные гигабайты не ложатся в память узла раньше
отказа. Части сообщения собираются вместе и считаются против
`max_message` вместе; ping и закрытие между ними — законны и места под
сообщение не занимают.

Своё сообщение уходит одним кадром. Маску ставит только клиент — свежим
ключом из `digest.urandom` на каждый кадр.

## Сжатие: `permessage-deflate`

Сообщения JSON — снимки состояния, списки, строки журнала — повторяют одни
и те же ключи и сжимаются в разы. Сжатие по RFC 7692 включает настройка
`compress` — у сервера и у клиента:

```lua
router.get('/ws', websocket.handler(session, { compress = true }))

local ws = websocket.connect('ws://127.0.0.1:8080/ws', { compress = true })
ws.compressed                                   --> true
```

Сервер с `compress` принимает предложение `permessage-deflate`, которое
браузеры шлют всегда; клиент с `compress` делает его сам. Договорились —
у обеих сторон `ws.compressed` равно `true`, и дальше всё прозрачно: `send`
сжимает, `receive` отдаёт разжатое. Не договорились — разговор идёт несжатым, как
без настройки: сервер без `compress` на предложение не отвечает, клиент без
`compress` его не делает.

| Предложение клиента | Ответ сервера |
|---|---|
| `permessage-deflate`, в том числе с `client_max_window_bits` (так у Chrome и Node) | `permessage-deflate; client_no_context_takeover` |
| … `; server_no_context_takeover` | то же и `; server_no_context_takeover` — свой словарь не держится |
| … `; server_max_window_bits=15` | то же и `; server_max_window_bits=15` |
| окно сервера меньше 15, незнакомый или повторённый параметр, негодное значение | предложение отклоняется: годится следующее либо рукопожатие идёт без сжатия |

Свой словарь сжатия держится от сообщения к сообщению: второе похожее
сообщение сжимается ссылками на первое. Словарь той стороны договор держать
не даёт — `client_no_context_takeover` в ответе сервера,
`server_no_context_takeover` в предложении клиента, — и каждое её сообщение
разжимается своим потоком [`tnt-compress`](https://github.com/tnt-skein/tnt-compress)
с пределом `max_message`. Предел считает разжатое: сто килобайт сжатых
нулей разжимаются в сотню мегабайт, и предел по сжатому их бы не заметил.

Клиент пакета предлагает `permessage-deflate; server_no_context_takeover`
и принимает ответ только с `server_no_context_takeover`; ответ не по RFC 7692
либо без него — отказ `refused`:

```lua
websocket.connect('ws://legacy.example.org/ws', { compress = true })
--> nil, сервер ответил на permessage-deflate не по RFC 7692: permessage-deflate
```

Пустое сообщение и управляющие кадры уходят несжатыми: RSV1 — знак
сообщения, а не соединения. Сжатие идёт под замком записи — сообщения
уходят в том порядке, в каком сжимались, иначе ссылки назад у той стороны
указали бы не туда; и сжатие, и разжатие уступают управление между кусками
работы по 64 КБ.

Узел без системной zlib узнаёт об этом при объявлении маршрута
и при `connect`, а не на первом сообщении:

```lua
websocket.handler(session, { compress = true })
--> настройки WebSocket.compress: нет системной библиотеки zlib: …
```

## Живость и закрытие

Кадры читает отдельный файбер — читатель: отвечает на ping, ведёт закрытие
и складывает сообщения в ящик на `backlog` мест, откуда их берёт `receive`.
Сессии, которая только шлёт, читать не нужно. Молчание дольше
`ping_interval` — повод послать ping; молчание ещё на столько же — обрыв
(1006): сторона, не отвечающая на ping, мертва, а TCP узнал бы об этом
через часы. Ping раньше минуты держит соединение и через прокси, которые
рвут простаивающее.

Закрытие — рукопожатие (§7.1.2). `ws:close(code, reason)` шлёт кадр
закрытия и ждёт ответа `close_timeout` от отправки кадра; сообщения той
стороны после нашего закрытия уже никто не ждёт. Миг срока отмечается
настоящими часами, остаток ожидания — от времени планировщика
(правило сроков [`tnt-clock`](https://github.com/tnt-skein/tnt-clock),
«Срок: миг — `monotonic`, остаток — `scheduler_now`»), и срок
перепроверяется после каждого пробуждения: работа без уступки перед
закрытием и побудка не от той стороны ожидание раньше срока не кончают. Закрытие той стороны получает
ответ эхом кода (§5.5.1) без причины; `receive` отдаёт пришедшее
до закрытия и только потом отвечает закрытием.

| Код | Имя | Когда |
|---|---|---|
| 1000 | `NORMAL` | разговор окончен как положено |
| 1001 | `GOING_AWAY` | сторона уходит |
| 1002 | `PROTOCOL_ERROR` | нарушение протокола |
| 1003 | `UNSUPPORTED_DATA` | данные не того вида |
| 1005 | `NO_STATUS` | закрытие пришло без кода (в кадре не ходит) |
| 1006 | `ABNORMAL` | оборвалось без закрытия (в кадре не ходит) |
| 1007 | `INVALID_DATA` | текст не в UTF-8 |
| 1008 | `POLICY_VIOLATION` | нарушение правил стороны |
| 1009 | `MESSAGE_TOO_BIG` | сообщение больше предела |
| 1010 | `MANDATORY_EXTENSION` | нет нужного клиенту расширения |
| 1011 | `INTERNAL_ERROR` | поломка стороны: упала сессия |
| 1012 | `SERVICE_RESTART` | сервер перезапускается |
| 1013 | `TRY_AGAIN_LATER` | перегрузка: предел сессий |
| 3000–4999 | — | свои коды библиотек и приложений |

## Настройки

Негодная настройка — бросок на строке, где её дали: при объявлении маршрута
и при `connect`, а не на первом кадре.

| Настройка | Где | По умолчанию | Что задаёт |
|---|---|---|---|
| `max_message` | оба | 1 МБ | сколько байт сообщения принять; у сжатого — разжатых |
| `ping_interval` | оба | 30 с | сколько молчания до ping |
| `send_timeout` | оба | 10 с | срок очереди записи и записи кадра, каждый |
| `close_timeout` | оба | 5 с | сколько ждать ответа на закрытие |
| `backlog` | оба | 16 | сколько непрочитанных сообщений держать |
| `compress` | оба | нет | договариваться ли о сжатии `permessage-deflate` |
| `protocols` | оба | — | подпротоколы: у сервера — по предпочтению, у клиента — предложить |
| `origins` | сервер | только свой | разрешённые источники страниц |
| `max_connections` | сервер | — | сколько сессий маршрута разом |
| `timeout` | клиент | 10 с | срок на соединение, TLS и рукопожатие вместе |
| `origin`, `headers` | клиент | — | заголовки рукопожатия |
| `verify`, `ca_file`, `ca_path` | клиент | проверять | сертификат у `wss://` (настройки `tnt-tls`) |

```lua
websocket.handler(session, { ping_interval = 0 })
--> настройки WebSocket.ping_interval — число больше 0, а не 0
websocket.connect('ws://x/', { headers = { ['x-token'] = 'a\r\nHost: evil' } })
--> настройки клиента WebSocket.headers[x-token] — строка по образцу ^[^\r\n]*$, …
```

## Клиент

Адрес — `ws://узел[:порт]/путь` или `wss://…`; негодный — бросок на строке
вызывающего (учётка в адресе и обрывок после `#` RFC 6455 запрещает).
Соединение, TLS и рукопожатие идут одним сроком `timeout`: миг срока
отмечается настоящими часами, остаток каждого ожидания — от времени
планировщика (правило сроков [`tnt-clock`](https://github.com/tnt-skein/tnt-clock),
«Срок: миг — `monotonic`, остаток — `scheduler_now`»). TLS —
[`tnt-tls`](https://github.com/tnt-skein/tnt-tls) с проверкой сертификата
по умолчанию.

Ответ сервера сверяется строго: 101, `Upgrade` и `Connection`, ответ на наш
ключ, подпротокол — из предложенных, расширение — только `permessage-deflate`
и только предложенное (`compress`): кадры с чужим расширением мы не прочли бы.
Голова ответа — не больше 16 КБ.

```lua
websocket.connect('ws://127.0.0.1:8080/nowhere')
--> nil, сервер не принял рукопожатие: 404        (err.status == 404)
websocket.connect('ws://127.0.0.1:1/')
--> nil, соединение с 127.0.0.1:1 не открылось: Connection refused
```

## За обратным прокси

Узел выходит в сеть только за обратным прокси (документ `tnt-router`,
«Выход в сеть: только за обратным прокси»), а прокси, который держит
соединения к узлу живыми пустым заголовком `Connection`, смену протокола
не пропустит. WebSocket нужен свой `location` рядом с общим
(`tarantool_app` — `upstream` узлов из образца того раздела):

```nginx
location /ws/ {
    proxy_pass http://tarantool_app;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 120s;    # дольше ping_interval: ping держит соединение
}
```

## Чем пришлось поступиться

- **Сжатие по умолчанию выключено.** Свой словарь сжатия живёт
  с соединением — до 256 КБ памяти zlib на каждое, вне арены Tarantool
  (замер на 3.8: 208 КБ после сообщения в 80 КБ), а сжатие и разжатие —
  счёт в потоке событий узла. Коротким командам сжатие почти ничего
  не даёт; включают его там, где сообщения большие и похожие друг на друга.
- **Словарь той стороны не держится.** Предел потока разжатия
  `tnt-compress` считает разжатое всех кусков вместе, и поток на всё
  соединение упёрся бы в `max_message` через мегабайт разговора. Поэтому
  каждое сообщение той стороны разжимается своим потоком, а сжимает она его
  без ссылок на прежние: её короткие сообщения сжимаются хуже.
- **Окно сжатия — только 15 бит.** Меньшего `tnt-compress` не умеет:
  предложение с `server_max_window_bits` меньше 15 сервер отклоняет,
  а `client_max_window_bits` клиент не предлагает.
- **Сообщение, сжатое с концом потока DEFLATE** (BFINAL, RFC 7692,
  §7.2.3.4), не читается — разрыв 1007: хвост `00 00 ff ff` ложится
  за конец потока, а формат `raw` лишнего после конца не прощает. Так
  сжимает только отправитель без сброса zlib; браузеры и Node шлют сброс.
- **Сообщение собирается в памяти целиком**, и отдаётся целиком: потока
  по кускам у `receive` нет. Потолок — `max_message`.
- **Своё сообщение уходит одним кадром.** Сообщение в сотни мегабайт держит
  замок записи всё время отправки — ping и pong ждут за ним.
- **Ответ на закрытие той стороны — эхо кода без причины.** Браузер
  в `onclose` видит код и пустую причину: он показывает причину нашего
  ответного кадра, а не свою.
- **Полный ящик останавливает читателя.** Сессия, которая не читает, пока
  та сторона шлёт, держит и ответы на ping, и её закрытие — та сторона может
  счесть соединение мёртвым. Наше закрытие в таком случае ждёт весь
  `close_timeout`: ответ застрял за полным ящиком.
- **Остановка сервера сессий не закрывает.** `httpd:stop()` закрывает
  только приём новых соединений; идущие сессии закрывает `close_all`
  конечной точки, и позвать его — забота того, кто объявил маршрут.
  Сессии маршрута с `handler` закрыть нечем: у обработчика-функции
  средств над сессиями нет.
- **Закрытое соединение держит сокет, пока сессия не вернулась.** Сокет
  у сервера закрывает `http.server`, когда сессия отдала ему соединение;
  сессия, которая ждёт не `receive`, а своё, узнаёт о закрытии только
  на следующем `receive` или `send`.
- **Предел сессий мягкий на рукопожатии.** Лишнее соединение, успевшее
  получить 101, закрывается кодом 1013 сразу после него, а не отказом 503.
- **`Origin` по умолчанию сверяется с `Host`.** За прокси, переписывающим
  `Host`, своя страница получает 403, пока источник не назван в `origins`.

## Проверки

Проверки лежат в `test/` и идут на luatest. Соединение проверяется
на настоящей паре сокетов (`socket.socketpair`): сроки, конец потока, запись
в полный буфер и отмена файбера держатся на ядре, и двойник сокета доказал бы
только, что пакет правильно разговаривает сам с собой. Байты кадров сверены
с примерами RFC 6455 (§5.7), ответ на ключ — с примером §1.3, сжатые
сообщения — с примерами RFC 7692 (§7.2.3).

- `frame_test.lua` — кадры: байты примеров RFC, три вида длины, маска,
  части, зарезервированные биты и незнакомые коды, бит сжатия RSV1
  по RFC 7692, управляющие кадры, предел места и кадр, оборванный в любом
  месте.
- `handshake_test.lua` — общее у сервера и клиента в рукопожатии: ответ
  на ключ, заголовки-списки, образцы ключа и подпротокола.
- `deflate_test.lua` — сжатие: байты примеров RFC 7692, словарь от сообщения
  к сообщению и без него, предел разжатого, ответ сервера на предложения
  браузеров, отклонённые предложения, сверка ответа клиентом.
- `codes_test.lua` — коды закрытия и отказ: какие коды ходят в кадре, текст
  отказа, роды.
- `settings_test.lua` — настройки: умолчания сервера и клиента, отказ
  на негодной с местом броска, сжатие на узле без zlib.
- `connection_test.lua` — соединение: части, ping посреди сообщения,
  закрытие с обеих сторон и одновременное, срок ответа на закрытие после
  работы без уступки, после побудки и ровно в свой миг, нарушения, пределы,
  keepalive, два писателя из разных файберов; сжатые сообщения — разжатие
  и его предел, сжатие со словарём и без, отмена сжатия под замком записи.
- `server_test.lua` — сторона сервера: проверки рукопожатия, источник
  страницы, подпротокол, сессия и её конец, упавшая сессия, контекст
  запроса, предел сессий, закрытие всех сессий конечной точки: обе стороны
  получают кадр с кодом, два молчащих клиента держат закрытие один срок,
  а не два; договор о сжатии и сжатая сессия.
- `client_test.lua` — клиент: разбор адреса, запрос рукопожатия, строгая
  сверка ответа, предел головы ответа, общий срок на соединение, TLS
  и рукопожатие, отказы TLS, предложение сжатия и сверка ответа на него.
- `websocket_test.lua` — стык: сервер пакета на маршруте настоящего роутера
  `tnt-router` и клиент пакета разговаривают через `http.server` на петле —
  и сжатыми сообщениями, когда сжатие включили обе стороны.
- `websocket_live_test.lua` — живая сверка с чужой реализацией: клиент
  `WebSocket` из Node (встроен с 22-й версии; undici — тот же договор WHATWG,
  что у браузеров): текст, двоичное, текст в 140 КБ, чистое закрытие своим
  кодом; тот же разговор со сжатием — клиент разжимает сжатое сервером
  одним словарём. Без Node проверка пропускается.

```sh
make deps          # инструменты проверок, зависимости пакета и соседи проверок в .rocks
```
